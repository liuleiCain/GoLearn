# Go 同步原语与锁实现详解

本文档总结 Go 标准库同步原语的设计思路，强调“快速路径 + 阻塞路径”的基本模式。

---

## 一、Mutex（互斥锁）

设计要点（概念级）：

- **快速路径**：CAS 尝试加锁，失败则进入慢路径。
- **慢路径**：进入等待队列，使用运行时信号量阻塞/唤醒。
- **公平性与吞吐**：在低竞争时追求速度，高竞争时避免饥饿。

```
Lock():
  if CAS(unlocked -> locked) return
  slowPath() // 进入等待队列，等待唤醒
```

---

## 二、RWMutex（读写锁）

核心思想：

- 读多写少场景可并发读取。
- 写入需要独占，通常会阻塞后续读者，避免写者饥饿。

常见实现思路（概念级）：

- 维护读者计数。
- 写者到来时阻塞新读者，等待当前读者退出。
- 通过信号量/通知机制唤醒写者或读者。

---

## 三、WaitGroup

设计要点：

- 内部维护“计数器 + 等待者数量”的原子状态。
- `Add` 增减计数，`Done` 等价于 `Add(-1)`。
- `Wait` 在计数归零前阻塞，阻塞使用运行时信号量实现。

---

## 四、Cond（条件变量）

设计要点：

- 与互斥锁配合使用。
- `Wait` 会释放锁并阻塞，`Signal/Broadcast` 唤醒等待者。
- 运行时通常使用通知列表（notify list）维护等待队列。

---

## 五、sync.Pool

设计要点：

- **per-P 本地缓存**：减少锁竞争。
- **victim 缓存**：跨 GC 周期的复用缓冲区。
- **可被 GC 清理**：Pool 不保证对象长期存在，只是“可丢弃”的缓存。

适用场景：
- 临时对象复用（如 bytes.Buffer、临时切片）
- 降低 GC 压力

不适用：
- 需要稳定持久对象的场景

---

## 六、与调度器的交互

- 阻塞在锁上的 goroutine 会被挂起（park），调度器会切换执行其他 G。
- 高竞争锁会增加调度开销，因此需要结合场景选择合适的同步原语。

---

## 七、代码示例

```go
// sync.Pool 的基本行为：对象可能被 GC 清理
func SyncPoolDemo() {
    var pool sync.Pool
    pool.New = func() any {
        return make([]byte, 1024)
    }

    buf := pool.Get().([]byte)
    pool.Put(buf)

    runtime.GC() // 可能清理缓存（不保证一定）

    buf2 := pool.Get().([]byte)
    fmt.Printf("buf2 len=%d cap=%d\n", len(buf2), cap(buf2))
}
```
